# PvZ-Portable 模组开发文档

> 面向模组开发者的完整指南：从空目录到发布一个能玩的内容模组。
> 配套实例：本目录（`examples/pvz-minimal-mod`，本文所有示例的来源）与 `pvz-example-mod`（事件 + Mixin 的完整参考，游戏仓库的兄弟仓库）。

---

## 1. 生态概览

PvZ-Portable 是植物大战僵尸 GOTY 的纯 Java 移植版，**运行在真实的 Fabric Loader 上**：

- 游戏本体对 Loader 而言是一个内置模组，mod id 为 `pvz-portable`；
- 模组就是**普通的 Fabric 模组**：在自己的 `fabric.mod.json` 里写 `"pvz-portable": "*"` 即可挂载，游戏出新版本不需要改模组；
- 游戏代码本身零 Fabric 依赖，只暴露钩子点（hook）和按 id 索引的定义表（`SeedType.MAX_SEED_TYPES=200` / `ZombieType.MAX_ZOMBIE_TYPES=100`，空行 = 未注册）；
- 功能通过 **fabric-api**（本生态自己的 API，五个模块）获得：事件监听、植物/僵尸注册、资源注入。

游戏源码分三层，写模组时会直接引用其中的类：

| 包 | 内容 | 常用类 |
|---|---|---|
| `lawn` | 游戏层 | `Board`、`Plant`、`Zombie`、`LawnApp`、`SeedType`、`ReanimationType` |
| `sexy` | 引擎层 | `Rect`、`Graphics`、`MemoryImage`、`Image` |
| `pvzp` | 移植运行时 | reanim、粒子、音频 |

### 参考项目

| 项目 | 位置 | 用途 |
|---|---|---|
| `pvz-minimal-mod` | **本目录**（游戏仓库 `examples/pvz-minimal-mod`） | **极简骨架**（本文的示例模组）：入口类 + 一个事件监听，无 Mixin |
| `pvz-example-mod` | 游戏仓库的兄弟仓库（`../pvz-example-mod`） | 完整参考：事件 API + 三个 Mixin（accessor / 注入） |
| `fabric-api` | `../fabric-api` | 模组 API（`api-base` / `api-events` / `api-plant` / `api-resource` / `api-zombie`） |
| `loom` | `../loom` | 模组 Gradle 工具链插件 `cn.enaium.fabricpvz.loom` |
| `PvZ-Portable` | **本仓库** | 游戏本体（源码可读，写 mixin 找注入点用）；`../PvZ-Portable-Cpp/` 是上游 C++ 源，行为对照用 |

> 本文所有"游戏仓库"指本仓库（pvz-portable）；示例模组就住在 `examples/pvz-minimal-mod`，`cd examples/pvz-minimal-mod` 即可开始。

## 2. 环境准备

| 依赖 | 版本 | 说明 |
|---|---|---|
| JDK | **25** | Gradle `--release 25`；`gradle.properties` 建议设 `org.gradle.java.installations.auto-download=false`（本机已装） |
| Gradle | wrapper 自带 | 项目里带 `gradlew` / `gradle/wrapper/`，无需手装 |
| loom 插件 | `cn.enaium.fabricpvz.loom` | Plugin Portal 有正式版；本地新构建的版本从 mavenLocal 解析 |

**首次从源码搭建发布链**（只用正式发布版本构建模组时可跳过）：

```bash
cd <游戏仓库> && ./gradlew publishToMavenLocal -x test    # 先发游戏坐标（API 编译依赖它）
cd ../fabric-api && ./gradlew publishToMavenLocal          # API 聚合 jar + 五个 api-* 模块
cd ../pvz-example-mod && ./gradlew publishToMavenLocal     # 端到端测试要加载的示例模组
```

> ⚠️ API 是"反向依赖"：`fabric-api` 编译时锁定 `pvz-portable:<版本>`。改了游戏代码后要重跑 `fabric-api` 的 `publishToMavenLocal`，否则本项目的测试会拿陈旧 API，症状是"测试莫名失败"而不是"缺步骤"。

## 3. 五分钟上手：极简模组

一个能加载、能改游戏行为的模组**只需要 5 个文件**（见 `pvz-minimal-mod`）：

```
pvz-minimal-mod/
├── gradlew / gradlew.bat / gradle/wrapper/     ← 从任一现成项目复制
├── settings.gradle.kts
├── build.gradle.kts
├── gradle.properties
└── src/main/
    ├── java/cn/enaium/fabricpvz/minimalmod/MinimalMod.java
    └── resources/fabric.mod.json
```

### 3.1 build.gradle.kts

```kotlin
plugins {
    id("cn.enaium.fabricpvz.loom") version "1.0.9"
}

dependencies {
    // 本地开发：指向本仓库 build 出的发行包（先在仓库根跑过 distZip；从 examples/pvz-minimal-mod 向上两级）
    pvz(files("../../build/distributions"))
    // 对着正式发布版本构建时改为：
    // pvz("cn.enaium.fabricpvz:pvz-portable:1.2.5")   // 工具链自动从 GitHub Release 下载
}

group = "cn.enaium.fabricpvz"
version = "1.0.0"
```

`pvz(...)` 是工具链的专用配置：它把游戏 jar 与发行包 `lib/` 里的全部启动库（Loader、Mixin、ASM、LWJGL、日志栈）一起放到编译/测试/启动类路径上，并生成 `runClient` 任务。**模组永远不要手动声明这些依赖。**

### 3.2 settings.gradle.kts

```kotlin
pluginManagement {
    repositories {
        mavenLocal()          // 本地新构建的 loom 插件从这里解析
        gradlePluginPortal()
        mavenCentral()
    }
}

dependencyResolutionManagement {
    repositories {
        mavenLocal()
        mavenCentral()
        maven { name = "Fabric"; url = uri("https://maven.fabricmc.net/") }  // Loader/Mixin 坐标
    }
}

rootProject.name = "pvz-minimal-mod"
```

### 3.3 gradle.properties

```properties
org.gradle.jvmargs=-Xmx2g -Duser.language=en -Duser.country=US
org.gradle.java.installations.auto-download=false
```

### 3.4 fabric.mod.json

```json
{
  "schemaVersion": 1,
  "id": "pvz-minimal-mod",
  "version": "1.0.0",
  "name": "PvZ Minimal Mod",
  "environment": "client",
  "entrypoints": {
    "main": ["cn.enaium.fabricpvz.minimalmod.MinimalMod"]
  },
  "depends": {
    "fabricloader": ">=0.19.0",
    "fabric-api": ">=1.1.0",
    "pvz-portable": "*"
  }
}
```

要点：

- `"pvz-portable": "*"` 是版本无关声明——游戏升级不用改模组；
- 用了 API 就要声明 `"fabric-api"`；**不用 API 的纯 Mixin 模组可以不写**；
- `environment: "client"`——游戏没有服务端概念。

### 3.5 入口类

```java
package cn.enaium.fabricpvz.minimalmod;

import cn.enaium.fabricpvz.api.lawn.LawnEvents;
import net.fabricmc.api.ModInitializer;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class MinimalMod implements ModInitializer {

    private static final Logger LOGGER = LoggerFactory.getLogger("pvz-minimal-mod");

    @Override
    public void onInitialize() {
        LOGGER.info("pvz-minimal-mod 已加载：阳光收取翻倍已开启");
        LawnEvents.SUN_COLLECTED.register((board, amount, source) -> amount * 2);
    }
}
```

- 入口类实现 `net.fabricmc.api.ModInitializer`，Loader 反射实例化后调 `onInitialize()`；
- 日志走 **SLF4J**：编译类路径上只有 API，Log4j 后端由启动库供齐，什么都不用声明；
- Kotlin 模组注意：入口必须写成 `class` 并保留无参构造（不能是 `object`），否则要用 fabric-language-kotlin 的语言适配器。

### 3.6 构建与验证

```bash
./gradlew build          # 产物在 build/libs/<id>-<version>.jar
./gradlew runClient      # 开发运行：模组自身输出 + fabric-api 在类路径上，改完代码直接跑
```

## 4. 安装与分发

正式版本的目录布局：

```
PvZ-Portable-1.2.5/
├── bin/、lib/               ← 发行包自带
├── mods/                    ← 手动创建，与 bin/ 同级
│   ├── fabric-api-<版本>.jar   ← API 聚合 jar（内嵌五个 api-* 模块）
│   └── 你的模组-1.0.0.jar
└── ...
```

**两条铁律：**

1. **模组不捆绑任何依赖**——Loader、Mixin、ASM、API 都在启动类路径或以 `fabric-api` 单 jar 形式进 mods/。模组 jar 里再嵌一份就是 bug，Loader 会静默任选其一。
2. mods/ 里只放 `fabric-api-<版本>.jar` **一个** API jar（聚合版，五个模块内嵌其中），不要把 api-base 等单独的 jar 也丢进去。

开发运行（`runClient`）与安装布局的区别：

| | `runClient`（开发运行） | 安装运行 |
|---|---|---|
| API 来源 | 类路径（工具链放入） | `mods/` 里的 fabric-api jar |
| 模组来源 | 自身输出目录 | `mods/` 里的模组 jar |
| `mods/` 目录 | 不读不写 | 玩家放置 |

> 坑：开发期间若曾在 `mods/` 放过同名旧 jar，Loader 会拿 `mods/` 里的那份而不是类路径上的新代码，且不报错——先删掉再 `runClient`。

## 5. 事件 API（api-events）

游戏在固定钩子点调用 `LawnHooks`，`api-events` 的桥把每次调用转成 Fabric 风格事件。**在 `onInitialize` 里注册监听即可，注册时机无关紧要**（Loader 不保证各模组入口的先后顺序）。

### 5.1 两类事件语义

- **通知型**（void）：按注册顺序逐个通知；
- **值链型**（有返回值）：监听器排成流水线，每个收到上一个的返回值、自己的返回值给下一个；没有任何监听时值原样通过——**没人监听就绝不改变游戏行为**；
- **可取消型**（boolean）：所有监听器 OR 起来，任一返回 true 即取消；
- 监听器抛出的异常不会被吞掉，会以 `ListenerException`（注明监听器）从游戏钩子点冒出来。

### 5.2 LawnEvents 全表（`cn.enaium.fabricpvz.api.lawn.LawnEvents`）

| 事件 | 签名 | 语义 |
|---|---|---|
| `LEVEL_START` | `(board, level, gameMode, background)` void | 关卡初始化完成、即将开跑 |
| `LEVEL_END` | `(board, result)` void | 关卡结束（胜/负），渐隐之前 |
| `WAVE_START` | `(board, waveIndex, zombieTypes)` → boolean | 一波僵尸即将刷出；true = 取消 |
| `ZOMBIE_SPAWN` | `(board, zombieType, row, fromWave)` → boolean | 僵尸即将上场；true = 取消刷出 |
| `ZOMBIE_DEATH` | `(board, zombie)` void | 僵尸死亡（掉落已由游戏结算） |
| `ZOMBIE_DAMAGE` | `(board, zombie, amount, damageFlags)` → int | 伤害即将结算；返回值替换伤害量 |
| `PLANT_PLACED` | `(board, plant, gridX, gridY)` void | 植物已种入网格 |
| `PLANT_REMOVED` | `(board, plant, cause)` void | 植物移除（被吃/铲除/爆炸…，cause 为游戏原因码） |
| `PLANT_DAMAGE` | `(board, plant, amount)` → int | 伤害即将结算；返回值替换伤害量 |
| `SUN_COLLECTED` | `(board, amount, source)` → int | 阳光（或硬币值）即将入账；返回值替换入账量 |
| `PLANTING_VALIDATED` | `(board, gridX, gridY, seedType, reason)` → int | 种植校验完成；返回 `PlantingReason_OK` 强制允许，其他值否决 |
| `TICK` | `(board, tick)` void | 一个游戏 tick（每秒 100 个），棋盘计数器推进后 |
| `PRE_DRAW` / `POST_DRAW` | `(board, graphics)` void | 棋盘对象绘制前/后 |

### 5.3 生命周期事件（`GameLifecycleEvents`）

| 事件 | 时机 |
|---|---|
| `INITIALIZED` | 游戏加载完资源组、建好 GL 接口之后 |
| `EXITING` | 退出前 |

### 5.4 自定义内容的逐实体事件（api-plant / api-zombie）

`LawnEvents` 面向整个棋盘；对自己注册的植物/僵尸，还有**按实例触发**的事件：

| 事件 | 签名 | 触发点 |
|---|---|---|
| `CustomPlantEvents.TICK` | `(plant)` void | 每个 `PlantType.builder().onTick(...)` 之外，也可以直接注册监听 |
| `CustomPlantEvents.PLACED` | `(plant, gridX, gridY)` void | 自定义植物种入网格 |
| `CustomZombieEvents.TICK` | `(zombie)` void | 自定义僵尸每 tick |
| `CustomZombieEvents.SPAWNED` | `(zombie)` void | 自定义僵尸上场（"现在归你管"的点，魅惑后也会走到这里） |

行为逻辑有两条等价路径：builder 的回调（`onTick`/`onPlanted`，见 §6）或**直接实现接口** `PlantBehaviour`（`onUpdate`/`onPlanted`/`plantRect`/`plantAttackRect`）与 `ZombieBehaviour`（`onUpdate`/`onSpawned`）——builder 内部就是把回调适配成这两个接口交给游戏。

### 5.5 示例：阳光翻倍（`pvz-minimal-mod` 的全部逻辑）

```java
LawnEvents.SUN_COLLECTED.register((board, amount, source) -> amount * 2);
```

## 5A. 修改现有内容（Override 体系）

不注册新内容、只调整原版数值/行为时用 Override。**每个类型至多一个覆写**（`of()` 幂等，后调的字段覆盖前调的）：

```java
// 植物覆写（PlantOverrides / PlantOverride）——入口点里调用
PlantOverrides.of(SeedType.SEED_CHOMPER)
        .cost(150)              // 定义字段：写入 PlantDefinition 表
        .refreshTime(5000)
        .bodyHealth(400)        // 出场字段：Plant::PlantInitialize 应用
        .crushProof(true);      // 战斗字段：碾压判定点读取
// 全局重平衡位（不属于某个种子类型）：
PlantOverrides.notOnGroundState(...);     // 替换"不在地面"状态
PlantOverrides.extraFireSeedType(...);    // 移动装弹中的额外射击

// 弹射物覆写（ProjectileOverrides）——立即写入 Projectile.gProjectileDefinition 行
ProjectileOverrides.of(ProjectileType.PROJECTILE_PEA).damage(25);
ProjectileOverrides.torchwoodConversion(          // 火炬树转化表：穿火后变什么
        ProjectileType.PROJECTILE_PEA, ProjectileType.PROJECTILE_FIREBALL);

// 僵尸覆写（ZombieOverrides / ZombieOverride）
ZombieOverrides.of(ZombieType.ZOMBIE_POLEVAULTER)
        .bodyHealth(500)
        .helm(HelmType.HELMTYPE_TRAFFIC_CONE, 300)   // 头防具类型与血量（HelmType 来自游戏层）
        .shieldHealth(0)
        .mindControlBodyHealth(...)    // 被魅惑后的血量
        .phaseCounter(...)
        .spawnsAs(ZombieType.ZOMBIE_NORMAL)  // 上场时以另一类型生成
        .bodyAnimation("...");
// 全局：
ZombieOverrides.mindControlBoost(bodyBonus, helmBonus, scale);  // 魅惑强化
ZombieOverrides.burnImmunity(totalHealth, phases...);           // 燃烧免疫（哪些阶段免疫火焰）
```

> ⚠️ **时序契约**：定义字段是普通表写入，游戏在创建实体/读表时取值——所以覆写必须在**模组入口点**（Loader 在游戏主类之前运行 `onInitialize`）里做，事后调用无效。读访问器（`registered()`/`damage()` 等）供诊断与测试用。

## 6. 注册内容（api-plant / api-zombie）

游戏本体不知道模组内容——注册由 API 的 Mixin 把定义行为注入游戏方法。已注册且已解锁的种子会出现在选卡界面原版网格之后的页；图鉴僵尸页会展示零售范围之上的每个已定义僵尸类型。

- 植物从 `PlantRegistry.FIRST_SEED_TYPE = 100` 起分配 id，僵尸从 `ZombieRegistry.FIRST_ZOMBIE_TYPE = 64` 起——**id 由注册器分配，不要手填**。

### 6.1 注册植物

```java
import cn.enaium.fabricpvz.api.plant.PlantType;
import cn.enaium.fabricpvz.portable.lawn.PlantSubClass;
import cn.enaium.fabricpvz.portable.lawn.ReanimationType;

public final class MyMod implements ModInitializer {

    public static final PlantType PEASHOOTER_PLUS = PlantType.builder("peashooter_plus")
            .name("双发豌豆+")
            .tooltip("一次吐两颗豌豆，贵一点点。")
            .cost(125)
            .reanimation(ReanimationType.REANIM_REPEATER)   // 借用双发豌豆的动作与卡面
            .subClass(PlantSubClass.SUBCLASS_SHOOTER)
            .launchRate(150)
            .burst(2)                                        // 每次齐射 2 发
            .health(400)
            .register();                                     // 一行完成注册

    @Override
    public void onInitialize() {
        // 从这里起种子可用；SeedType 值 = PEASHOOTER_PLUS.seedType()
    }
}
```

Builder 常用方法（全部可省，默认值见 `CustomPlantType` 字段）：

| 分组 | 方法 |
|---|---|
| 文案 | `name` / `tooltip` / `almanacDescription` / `stringKeyStem`（留空则按上游方式读游戏字符串文件） |
| 数值 | `cost` / `refreshTime`（厘米秒）/ `health` / `launchRate` / `burst`(1/2/4) |
| 形象 | `reanimation(类型)` / `packetArtFromReanimation()` / `packetArt(imageId, celIndex)` / `packetArt(Supplier<Image>)`（运行时画的卡面，资源晚加载也能补上） |
| 行为 | `subClass` / `projectile` / `onTick` / `onPlanted` / `plantRect` / `plantAttackRect` / `plantingRule` |
| 特性 | `aquatic` / `fungus` / `nocturnal` / `flying` / `upgrade` / `upgradeFrom(SeedType...)` |
| 选卡 | `unlockAfter(前置SeedType)` / `invisible` / `chooserVisible` |

配套查询/操作：`PlantRegistry.get(id|String)`、`all()`、`unregister(id)`、`canPlantAt(board, x, y, seedType)`、`place(board, x, y, seedType)`。

### 6.2 注册僵尸

```java
import cn.enaium.fabricpvz.api.zombie.ZombieType;
import cn.enaium.fabricpvz.portable.lawn.ReanimationType;

public static final ZombieType RUNNER = ZombieType.builder("runner")
        .name("飞毛腿僵尸")
        .health(400)
        .bodyReanimation(ReanimationType.REANIM_ZOMBIE)
        .wave(2, 1, 5, 2000)      // 点数, 出现起始关卡, 首次波次, 选取权重
        .register();

// 之后 Board::AddZombieInRow(RUNNER.zombieType(), row, fromWave) 即可用
```

僵尸 Builder 其余可用项：头部配件（`headReanimation` / `headTrack` / `headTransform`）、防具（`helm` / `shield` / `flyingHealth`）、碰撞盒（`collider` / `attackRect`）、外观（`scale`）、特性（`canGoInPool`）、出场（`points` / `pickWeight` / `startingLevel`）、行为（`onTick`）。查询/操作：`ZombieRegistry.get/all/unregister`、`spawn(board, type, row, fromWave)`。

## 7. 资源（api-resource）

### 7.1 造图：`ModImages`（纯像素工具，不绑进游戏）

```java
MemoryImage art = ModImages.load(MyMod.class, "art/red_peashooter.png");  // 从模组 jar 的 classpath 读 PNG
MemoryImage canvas = ModImages.blank(80, 80);
MemoryImage painted = ModImages.painted(80, 80, g -> { /* 用 Graphics 画 */ });
MemoryImage tinted = ModImages.remapHue(source, 120.0f, 0.5f);            // 色相重映射
```

### 7.2 绑进游戏

| API | 用途 |
|---|---|
| `ModImageSlot.claim(modId, name)` | 申领一个游戏图槽，把 `ModImages` 造的图放入供游戏绘制 |
| `GameArt.packetArt(seedType)` / `cachedPlantFrame(seedType)` | 读取游戏现有的卡面 / 缓存植株帧 |
| `GameArt.installCachedPlantFrame(seedType, image)` | 安装缓存植株帧（改造原版外观） |
| `ModReanims.overrideTrackArt(reanim, trackNames, mapper)` | 覆盖 reanimation 的轨道贴图（换装/换肤的正规入口） |
| `ModReanims.overrideTrackArt(reanim, Function<Image,Image>)` | 全轨道统一变换 |
| `ModReanims.giveSeparateHeadLayer(plant)` | 给植物独立头部层 |
| `ResourceInitializer` / `ResourceDiagnostics` | 资源初始化钩子与诊断 |

### 7.3 替换游戏文件：`ResourceOverrides`

按 pak 路径**整文件替换**原版素材——不改 `main.pak` 就能换图/换字体/换打包文件的正规入口：

```java
ResourceOverrides.addFile("images/peashooter.png", Path.of("my-peashooter.png")); // 覆盖单个文件
ResourceOverrides.addBytes("properties/LawnStrings.txt", myBytes);                // 直接给字节
ResourceOverrides.addRoot(Path.of("res-root"));                                   // 整目录映射
```

运行时游戏按 pak 路径解析时优先取覆盖内容；`overriddenNames()`/`resolveOverride(pakPath)` 供诊断。资源在 `GameLifecycleEvents.INITIALIZED` 后才算就绪——运行时画的卡面（§6.1 的 `packetArt(Supplier)`）在资源未加载时返回 null 即可，游戏会先保留原样绘制。

### 7.4 模组自己的字符串（api-base `Translations`）

```java
Translations.install((key, fallback) -> /* 查自己的表，查不到返回 null 走 fallback */);
String name = Translations.translate("plant.mymod.xxx", "默认名");
```

游戏语言（`language()`）变化时查同一张表即可；`active()` 报告是否有人安装了 Source。

### 7.5 模组间协作（api-base `ModQuery` / `PvzFabricApi`）

```java
ModQuery.isModLoaded("pvz-example-mod");          // 联动检测
ModQuery.getModVersion("pvz-portable");           // 版本探测
PvzFabricApi.isInitialized() / getVersion();      // API 状态与版本
PvzFabricApi.getMods() / getEntrypoints(key, t);  // 模组列表 / 自定义入口点
```

## 8. Mixin 开发（进阶）

**能力边界**：API 的事件、注册与覆写覆盖了游戏性行为（实体、数值、资源、绘制前后），但仍有 API 未暴露的面——界面与对话框（菜单/商店/图鉴的布局）、关卡与挑战模式注册、成就系统等。这些用 Mixin 直接注入游戏类解决。

Mixin 子系统由 Loader 自带（Sponge Mixin + ASM），**模组侧零额外依赖**：注解在编译类路径上（工具链供齐），运行期转换由 Loader 完成。Mixin 目标是 `cn.enaium.fabricpvz.portable.*` 的游戏类——`src/main` 的游戏代码没有 Fabric 依赖，也 mixin 不到 `net.fabricmc.*`。

> 找注入点的方法：游戏源码每个方法都带 `Ported from src/Lawn/Board.cpp:246` 标记——在 `PvZ-Portable` 仓库里全文检索行为关键词，顺着 Ported 标记定位到 Java 方法与上游行号，`../PvZ-Portable-Cpp/` 里还能对照上游实现理解语义。

### 8.1 接线：两处声明

`fabric.mod.json` 追加：

```json
"mixins": ["examplemod.mixins.json"]
```

`src/main/resources/examplemod.mixins.json`：

```json
{
  "required": true,
  "minVersion": "0.8",
  "package": "cn.enaium.fabricpvz.examplemod.mixin",
  "compatibilityLevel": "JAVA_25",
  "mixins": ["BoardAccessor", "BoardMixin", "LawnCommonMixin"],
  "injectors": { "defaultRequire": 1 }
}
```

- `"required": true` + `"defaultRequire": 1`：注入点找不到（游戏改了方法签名）时**启动直接失败**而不是静默失效——这是想要的，静默失效的模组最难排查；
- mixin 类都放在独立包（`...mixin`），不与模组业务类混放。

### 8.2 @Inject：往方法里加代码（最常用）

实例方法注入 + `@Shadow` 读游戏私有字段（`pvz-example-mod` 的 `BoardMixin` 原文）：

```java
@Mixin(Board.class)
public final class BoardMixin {

    @Shadow
    private int mSunMoney;                     // 游戏字段在 mixin 里"影子化"后可直接引用

    @Inject(method = "update()V", at = @At("HEAD"))   // 棋盘 tick 的开头
    private void examplemod$onBoardUpdate(CallbackInfo ci) {
        ExampleMod.boardUpdates++;
        ExampleMod.lastObservedSun = this.mSunMoney;
    }

    // 目标方法带返回值 → 用 CallbackInfoReturnable，泛型对准返回类型
    @Inject(method = "canTakeSunMoney(I)Z", at = @At("HEAD"))
    private void examplemod$observeSunSpending(int theAmount, CallbackInfoReturnable<Boolean> cir) {
        ExampleMod.lastObservedSun = this.mSunMoney;
    }
}
```

要点：

- **`method` 用字节码签名**：`"update()V"`、`"canTakeSunMoney(I)Z"`——重载方法必须靠参数类型区分，只写方法名会在有重载时失败；
- **处理器命名 `模组id$功能`**：mixin 类会被合并进目标类，不加前缀的方法名可能撞上游戏自己的方法；
- `@At("HEAD")` 之外常用：`@At("RETURN")`（返回前，所有 return 点）、`@At("TAIL")`（方法末尾）、`@At(value = "INVOKE", target = "L...;xxx()V")`（某个调用点前后）；
- **取消执行**：`ci.cancel()`（void 方法）或 `cir.setReturnValue(值)` + `cir.cancel()`（改写返回值）——事件 API 已覆盖的行为优先用事件，别用 Mixin 硬来。

静态方法的注入（`LawnCommonMixin` 原文）——处理器加 `static`：

```java
@Mixin(LawnCommon.class)
public final class LawnCommonMixin {

    @Inject(method = "modInRange(II)Z", at = @At("HEAD"))
    private static void examplemod$markMixinApplied(int theNumber, int theMod,
            CallbackInfoReturnable<Boolean> cir) {
        ExampleMod.mixinApplied = true;
    }
}
```

### 8.3 @Accessor：读写私有字段（不改行为）

接口式 mixin，引擎把这个接口加到目标类上并生成桥接实现（`pvz-example-mod` 的 `BoardAccessor` 原文）：

```java
@Mixin(Board.class)
public interface BoardAccessor {

    @Accessor("mSunMoney")
    int examplemod$getSun();

    @Accessor("mSunMoney")
    void examplemod$setSun(int value);      // getter/setter 成对，字段名对准游戏源码
}
```

使用时把实例强转成接口（mixin 后的对象**真的实现了**这个接口）：

```java
Board board = ...;
int sun = ((BoardAccessor) (Object) board).examplemod$getSun();
```

### 8.4 @Redirect / @ModifyArg：改掉一次调用（用前先想事件）

把游戏对某方法的一次调用替换成自己的逻辑：

```java
@Redirect(method = "update()V",
          at = @At(value = "INVOKE", target = "Lcn/enaium/fabricpvz/portable/lawn/Plant;update()V"))
private void examplemod$wrapPlantUpdate(Plant plant) {
    plant.update();
    // 前后追加逻辑……
}
```

- `@Redirect` 整个接管这次调用（可以不调原方法）；`@ModifyArg` 只改传进去的某个参数；
- **撞车风险**：两个模组 `@Redirect` 同一个调用点会直接冲突（Redirect 天生互斥），公开模组尽量少用；`@ModifyArg` 的相容性更好；
- 目标描述符写全限定名（`Lcn/enaium/fabricpvz/portable/...`，斜杠分隔），写错在加载期就报 `InjectionError`——配合 `defaultRequire: 1` 是快速反馈。

### 8.5 开发与调试循环

```bash
./gradlew build        # mixin 配置 json 不合法 / 类名拼错 → 编译期或加载期立刻红
./gradlew runClient    # 启动即完成全部 mixin 转换；失败信息带具体类与方法
```

- **启动日志**里搜 `mixin`：转换失败会打印目标类、方法签名与原因；
- 注入点验证发生在游戏类**首次加载**时——某个 mixin 只在进关卡后才触发转换失败的话，症状是"启动正常，进关卡崩"，排查时先看崩的那条栈里的 mixin 名；
- 改 mixin 后要完全重启 `runClient`，热重载不存在；
- `defaultRequire` 期间可以临时降到 0 让游戏带病启动（只为看其他日志），发布前必须改回 1；
- 游戏版本升级后 mixin 失效的典型报错是 `InjectionError: ... critical injection failure`——按 §9 的版本对照表换 `pvz(...)` 指向新发行包，再按新的方法签名修 `method =` 即可；写事件 API 能实现的行为就不要写 mixin，游戏升级时事件签名由 API 维护、模组零改动。

### 8.6 三条纪律

1. **能用事件/Override 就不写 Mixin**（§5/§5A/§6）——API 面由生态维护、跨版本稳定，mixin 面是你和游戏源码的私人契约；
2. **mixin 类只放 mixin**——业务逻辑写在模组自己的类里，mixin 处理器只做转发（看 example-mod：处理器一行计数/赋值，逻辑都在 `ExampleMod`）；
3. **处理器一律带模组前缀**（`examplemod$…`）——mixin 类合并进目标类后，命名冲突不是编译错误而是加载期怪病。

## 9. 版本对应与发布

| 位置 | 版本含义 |
|---|---|
| 模组 `build.gradle.kts` 的 `pvz(...)` | 对哪个游戏发行包构建（发布版坐标或本地 distributions） |
| 模组 `fabric.mod.json` 的 `version` | 模组自己的版本 |
| `"pvz-portable": "*"` | **永远写星号**，游戏升级零成本 |
| loom 插件 `GAME_VERSION` | 工具链默认下载的游戏版本 |

发布就是把 `build/libs/<id>-<版本>.jar` 发出去，附一句安装说明：**放入版本目录的 `mods/`，并需同时安装 `fabric-api-<版本>.jar`**。

## 10. 常见问题速查

| 症状 | 原因与解法 |
|---|---|
| Override（改原版数值）不生效 | 调用时机太晚——必须在模组入口点里做（§5A 时序契约） |
| 启动/进关卡报 `InjectionError: critical injection failure` | mixin 的 `method`/`target` 签名与当前游戏不符；对照游戏源码修签名（§8.5） |
| 两个模组同用 `@Redirect` 后启动冲突 | Redirect 天生互斥，改 `@ModifyArg` 或事件（§8.4） |
| 启动报 `需要 fabric-api 的 x.y 及以上版本，但没有安装它` | mods/ 里缺 `fabric-api-<版本>.jar`（§4） |
| 改了代码 `runClient` 没生效 | `mods/` 里有同名旧 jar，Loader 静默取旧（§4 坑） |
| 测试报 API 类不存在 / 行为陈旧 | mavenLocal 里的 API 过期；重跑 `fabric-api` 的 `publishToMavenLocal`（§2） |
| `pvz(...)` 解析失败 | 本地开发时确认游戏仓库根的 `build/distributions` 存在（先在仓库根 `distZip`），或改用发布版坐标 |
| Gradle 找不到 JDK 25 | `JAVA_HOME` 指向已装的 JDK 25；`auto-download=false` 时不会自动下载 |
| Kotlin 模组入口实例化失败 | 入口写成 `class` 而非 `object`（§3.5） |
| 模组日志一条都没出现 | 入口类没写进 `fabric.mod.json` 的 `entrypoints.main`，或类名/包名不匹配 |
| 监听器异常悄悄消失 | 不会消失——会包成 `ListenerException` 从游戏钩子点抛出（§5.1） |
